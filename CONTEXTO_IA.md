# Contexto para IAs — Projeto NutriMirim

Este arquivo guarda o histórico do que as IAs (Claude, ChatGPT, Gemini, Copilot etc.) já fizeram no projeto e o registro dos prompts usados pelos integrantes. Todas as LLMs que trabalharem no projeto devem ler este arquivo antes de começar e registrar aqui o que fizeram.

---

## 🤖 Instrução para a IA (leia antes de qualquer tarefa)

> **Se você é uma IA trabalhando neste repositório, siga estas regras:**
>
> 1. **Leia este arquivo inteiro antes de começar.** Ele resume o projeto, o que já foi feito e as decisões tomadas. Não refaça trabalho que já está registrado aqui e não contrarie decisões registradas sem avisar o integrante.
> 2. **Ao terminar a tarefa, registre o que fez.** Adicione uma linha no fim da tabela da seção "Registro de prompts", com: data, integrante, ferramenta/modelo, o prompt **exatamente como foi escrito** (sem corrigir) e um resumo curto do que foi feito e de quais arquivos mudaram.
> 3. **Se a tarefa mudou o projeto** (nova tela, nova regra, nova decisão), atualize também a seção "Decisões e cuidados" ou "Pendências conhecidas". Se concluiu uma task da divisão, troque o status dela para ✅ (ou 🟡 se ficou parte por fazer).
> 4. **Não apague nem reescreva registros antigos.** Só acrescente.
> 5. Responda em **português**, inclusive nas mensagens de commit (ver o padrão em "Decisões e cuidados").
> 6. **Nunca commite direto na `main` nem na `develop`.** Trabalhe numa branch da task e siga a seção "Como subir sua task (branches)".
> 7. Se você não puder editar arquivos (ex.: chat no navegador), entregue no fim da resposta a linha pronta para o integrante colar na tabela.

- **O que é:** app de vigilância nutricional infantil para apoiar Agentes Comunitários de Saúde (ACS), pediatras e nutricionistas no combate à desnutrição e ao nanismo em comunidades carentes e UBS.

## Decisões e cuidados

- **Dados mock são fictícios.** Nomes, endereço e CPF em `lib/data/mock_data.dart` são inventados. Nunca usar dados reais de crianças ou responsáveis (LGPD).
- **O resultado nutricional é ilustrativo.** O cálculo de z-score ainda não segue as tabelas oficiais da OMS; a tela mostra um aviso disso. Não remover o aviso enquanto o cálculo não for real.
- **Fidelidade ao protótipo.** As telas seguem o protótipo de alta fidelidade (`docs/prototipoAltaFidelidade.pdf`). Mudanças visuais devem ser combinadas com o grupo.
- **Acessibilidade.** As cores foram escolhidas para contraste AA, e os testes verificam isso. Manter os testes passando ao mudar cores.
- **Tela pequena.** Os testes checam overflow em 360 dp de largura.
- **Commits em português.** Toda mensagem de commit é escrita em português, no formato `tipo: descrição curta`, com o verbo no presente. Tipos usados: `feat` (funcionalidade/tela), `fix` (correção), `test` (testes), `docs` (documentação), `chore` (configuração e arquivos de apoio) e `refactor` (reorganização sem mudar o comportamento). Exemplos: `feat: telas 01-12 fiéis ao protótipo do Figma` e `fix: barra inferior não duplica a Home`.
- **Modelos e ids (11/11/2026).** `Crianca` tem `id` (`c0` a `c10` no mock) e `Avaliacao` guarda `criancaId`. Busque sempre por id. Nas telas, use os repositórios (ver "Repositórios" abaixo); `MockData.criancaPorId(id)`, `MockData.avaliacoesDe(criancaId)` e `MockData.ultimaAvaliacaoDe(criancaId)` ficam só para o mock e os testes. Nunca busque por nome. As listas do mock são imutáveis; quando for preciso salvar, use os repositórios (back-end), não `MockData.criancas.add`.
- **Datas.** `cadastradoEm`, `nascimento` (pode ser nulo: "Não informado") e `Avaliacao.data` são `DateTime` local. Datas sem hora (nascimento, cadastro) devem ser gravadas no Firestore como texto `aaaa-mm-dd` ou ao meio-dia, nunca à meia-noite UTC, para não aparecer o dia anterior no fuso de Brasília.
- **Formatação.** Use só `lib/utils/formatters.dart`: `formatarData`, `formatarDataHora`, `formatarDecimal`, `formatarNumero`, `formatarPeso`, `formatarAltura`, `idadeEmMeses` e `formatarIdade`. Abaixo de 24 meses a idade fica só em meses ("18 meses"), como na caderneta e nas curvas da OMS.
- **Navegação entre telas.** Para a task da Lorena e os repositórios, a recomendação é passar o `id` da criança como argumento da rota, e não o objeto `Crianca` inteiro.
- **Classificação nutricional (18/11/2026).** `lib/services/classificacao.dart` (Dart puro) segue as fontes oficiais, e não o mock. **Pontos de corte:** os do SISVAN para 0 a 5 anos (MS, "Orientações para a coleta e análise de dados antropométricos", 2011), sem faixas inventadas: -1,8 é adequado. **Cores** (convenção do app, porque o SISVAN não define cor): verde para a faixa adequada, amarelo para peso elevado para a idade, risco de sobrepeso e sobrepeso, e vermelho para z < -2 e obesidade; z < -3 é `grave`. **Alerta (RF12):** aparece em todo vermelho. É urgente (encaminhar no mesmo dia) só na magreza acentuada (P/E ou IMC/I < -3), que é a desnutrição aguda grave da OMS e do AIDPI; muito baixo peso e muito baixa estatura geram alerta prioritário. O z-score não detecta edema, por isso as condutas pedem para verificar inchaço nos dois pés. **Retorno (RF17):** 5 dias se grave (AIDPI, "peso muito baixo") e 30 dias para os outros vermelhos e amarelos (AIDPI, "peso baixo"). Na faixa adequada, o retorno é a próxima consulta do calendário mínimo do MS (1ª semana, 1, 2, 4, 6, 9, 12, 18 e 24 meses, depois uma por ano), e sem a data de nascimento a função devolve `null` para o profissional definir. Isso substitui o exemplo de 180 dias do RF17. **A conferir na versão oficial do AIDPI 2017:** o retorno de 30 dias para excesso de peso e o esquema completo do peso muito baixo (5 dias, depois 14 e 30). As chaves de `IndicadorAntropometrico` (`pi`, `ei`, `pe`, `imci`) são as do Firestore. A ligação de `Gravidade` ao `Situacao` é `situacaoDe` em `lib/services/resultado_nutricional.dart`.
- **Curva de crescimento (18/11/2026; OMS em 24/11/2026).** A tela 08 recebe a criança pela rota: o `id` (recomendado) ou o objeto `Crianca`; sem argumento, mostra a criança em destaque. As linhas -3, -2, 0, +2 e +3 são calculadas das tabelas LMS da OMS 2006 (`CurvaReferencia.oms` em `lib/data/curvas_referencia.dart`, com `TabelasOms.valorReferencia`), as mesmas do z-score; as curvas aproximadas foram removidas. P/E usa a tabela por comprimento (45 a 110 cm) antes dos 2 anos e por altura (65 a 120 cm) depois. O card da última avaliação mostra o z-score e o percentil do indicador da aba (`lib/services/zscore_avaliacao.dart`): usa o valor gravado em `Avaliacao.indicadores` quando existe e, senão, calcula sem edema, que a avaliação não guarda. Se as tabelas não carregarem, a tela mostra os eixos, os pontos e um aviso. O gráfico usa o `textScaler` e mede os rótulos para definir as margens.
- **Resultado (24/11/2026).** `lib/services/resultado_nutricional.dart` junta os z-scores de `antropometria_oms.dart` (Larissa) com o `classificacao.dart`, sem outra cópia das tabelas. Só gera resultado sem erro de entrada e sem z-score fora dos limites de plausibilidade: medida a conferir não é classificada, para não classificar erro de digitação. **Edema bilateral** (informado na 06) é desnutrição aguda grave pela OMS em qualquer z-score: `ClassificacaoAvaliacao(edema: true)` dá gravidade `grave`, alerta urgente e retorno em 5 dias, mesmo sem os indicadores de peso. A 07 abre o alerta (RF12) em modal e mostra classificação, indicadores indisponíveis com o motivo, retorno e condutas. `ResultadoAvaliacao`, `MockData.resultadoNormal` e `resultadoDesnutricao` foram removidos. A avaliação ainda não é salva (task da Larissa).
- **Perfis de acesso (11/11/2026).** São 4 papéis: `master`, `acs`, `medico` e `nutricionista`. Os três últimos fazem tudo no app (crianças e avaliações) nas UBS da própria lista (`ubsIds`; o médico pode estar em mais de uma UBS). O `master` é o responsável pelo app: vê e grava os dados de todas as UBS, cadastra os usuários e as UBS. Ter poucos masters, porque ele acessa dados de crianças de todas as unidades (LGPD). Detalhes, campos e regras em [`docs/firestore.md`](docs/firestore.md).
- **Papéis no app (24/11/2026).** As **permissões continuam iguais** para `acs`, `medico` e `nutricionista` (regras e testes de 11/11 mantidos), mas **cada papel aparece no app pelo que tem de diferente no trabalho**: o **ACS** vê a Lista e o Início filtrados pela própria `microarea` (com a opção "ver toda a UBS"); o **médico** tem um seletor de UBS (`ubsIds`/`ubsAtualId`), e a criança nova vai para a UBS escolhida; a **nutricionista** (e o médico) veem no Resultado o detalhe técnico (z-score dos 4 indicadores e condutas completas), e o ACS vê o semáforo, a conduta resumida e o alerta (**decidir com o grupo**, porque o protótipo é igual para todos); **todos** veem no Perfil o nome, o papel, a UBS e a microárea reais, e o Histórico mostra quem fez cada avaliação. O **master** cadastra profissionais e UBS **pelo Console do Firebase** até 01/12, seguindo [`docs/cadastro-de-profissionais.md`](docs/cadastro-de-profissionais.md); tela de cadastro no app (com Cloud Function) fica para depois. O papel vem de `SessaoProfissional.papel` (`lib/repositories/sessao_profissional.dart`), montada no login; nunca decidir o papel pelo e-mail nem por dado local. Divisão em "Papéis no app" nas pendências.
- **Firestore.** Toda correção ou exclusão de avaliação (até 15 min, só o autor; o master a qualquer momento) e toda edição de criança exigem motivo e gravam o histórico em `alteracoes/{versao}` no mesmo lote; as regras recusam o que vier sem isso. Nada é apagado: criança e UBS são desativadas. Rodar os testes das regras: `cd firebase`, `npm install`, `npm test` (precisa de Node 24.12+ e Java).
- **Cores e alto contraste (18/11/2026).** Cores que mudam com o "Alto Contraste" (texto, texto secundário, bordas, ícones, fundo e superfície) vêm de `context.cores` (`lib/theme/app_palette.dart`, um `ThemeExtension`), e não de `AppColors`. Exemplo: `TextStyle(color: context.cores.textoSecundario)` no lugar de `AppColors.textMuted`. Cores de marca e de status continuam em `AppColors`. Quando a cor vier do `context`, tire o `const` do widget. Borda de campo e controle usa `cores.borda` (3:1); borda de cartão e divisória usa `cores.bordaSuave`. Fonte mínima de 12 px.
- **Firebase (18/11/2026).** Projeto `app-nutrimirim` (criado pelo Alexandre), com apps Android, iOS e Web registrados (pacote `br.com.nutrimirim.appnutrimirim`). O `lib/firebase_options.dart` e o `android/app/google-services.json` são versionados: as chaves do Firebase não são senhas, e a proteção dos dados são as regras do Firestore. O `main.dart` chama `Firebase.initializeApp` antes do `runApp`; os testes de widget montam o `NutriMirimApp` direto e não precisam do Firebase. Para rodar no Chrome, o `pubspec.yaml` precisa de `flutter_web_plugins` (SDK). **Versões (22/11/2026):** o projeto precisa compilar no Flutter 3.35.3 (Dart 3.9.2). Antes de adicionar um pacote, confira o `environment` dele no pub.dev; o `firebase_auth` está fixo em `7.0.1` por isso. Quem usa um Flutter mais novo não deve commitar o `pubspec.lock` reescrito pelo `pub get` (ele sobe os pacotes fixados pelo SDK e o mínimo do Dart): acrescente só as linhas dos pacotes novos. Para adicionar outra plataforma, rode de novo `flutterfire configure --project=app-nutrimirim`. Quem precisar mexer no Console pede ao Alexandre para ser adicionado ao projeto.
- **Repositórios (22/11/2026).** As telas leem dados só por `Repositorios.criancas` e `Repositorios.avaliacoes` (`lib/repositories/`), nunca por `MockData` nem pelo Firebase direto. O `MockData` só alimenta a versão em memória, que é a padrão do app e dos testes (chame `Repositorios.reiniciar()` no `setUp`). Depois do login (task do Alexandre), monte uma `SessaoProfissional` (uid, nome, papel, `ubsIds`, `ubsAtualId`, `microarea`, `nomesUbs`) e chame `Repositorios.usarFirestore(sessao)`. A API é assíncrona: listas e ficha são `Stream` (`observarTodas`, `observarDe`, `observarPorId`), e as gravações (`cadastrar`, `editar`, `desativar`, `registrar`, `corrigir`, `excluir`) lançam exceções de `lib/repositories/excecoes.dart` (`MotivoObrigatorio`, `PrazoCorrecaoExpirado`, `DadosInvalidos`, `EstadoInvalido`, `PermissaoNegada`, `NaoEncontrado`). Edição, desativação, correção e exclusão exigem motivo (3 a 200 caracteres) e gravam o log no mesmo lote. **`registrar` e `corrigir` exigem pelo menos um indicador** em `Avaliacao.indicadores` (chaves `pi`, `ei`, `pe`, `imci`), porque as regras do Firestore recusam sem isso. CPF com tamanho diferente de 11 dígitos e telefone diferente de 10 ou 11 dão `DadosInvalidos`; CPF mascarado com `*` mantém o valor já gravado. Busca sem acento com `normalizarBusca` (`lib/utils/texto.dart`) e `filtrarCriancas` (`lib/repositories/busca.dart`), que também acha por CPF. `porId` e `observarPorId` incluem crianças desativadas: as telas mostram "Cadastro desativado" e bloqueiam editar e registrar. Id inexistente mostra "Criança não encontrada.".
- **Autenticação (22/11/2026, PR #28).** As telas usam só a interface `AuthService` (`lib/services/auth_service.dart`), pela variável global `authService` de `lib/app_state.dart`. O `main.dart` coloca o `FirebaseAuthService`; nos testes fica o `AuthServiceMemoria` (para simular contas: `authService = AuthServiceMemoria(contas: {'email': 'senha'})` no `setUp`). Login só por e-mail e senha (provedor ativado no Console); as contas são criadas pelo master, não há cadastro pelo app. A Abertura (01) usa `restaurarSessao()` e vai direto ao Início se já houver sessão. Erros do Firebase viram mensagens em português em `FirebaseAuthService.mensagemDoErro`; "usuário não existe" e "senha errada" têm a mesma mensagem de propósito. A 02A só aceita e-mail (o Firebase não envia o link por telefone). **A 02C (nova senha) ficou como no protótipo, mas não muda a senha de verdade:** quem troca é a página do Firebase aberta pelo link do e-mail. Decidir com o grupo se a 02B deve trocar "Já recebi o link" por "Voltar ao login". **O login ainda não liga os repositórios ao Firestore:** depois do `entrar`/`restaurarSessao`, falta ler `profissionais/{uid}`, montar a `SessaoProfissional` e chamar `Repositorios.usarFirestore(sessao)`; no "Sair da conta", chamar `Repositorios.reiniciar()`. Até isso entrar, o app logado continua mostrando os dados do mock.
- **Contas de teste (25/11/2026).** UBS `ubs-centro` (UBS Centro) e `ubs-norte` (UBS Norte), em Aracaju. Contas criadas no Console, com perfis em `profissionais/{uid}`: `davisant28+master@gmail.com` (`master`, sem UBS), `davisant28+acs@gmail.com` (`acs`, `ubs-centro`, microárea `03`), `davisant28+medico@gmail.com` (`medico`, `ubs-centro` e `ubs-norte`) e `davisant28+nutri@gmail.com` (`nutricionista`, `ubs-centro`). - **Sessão do profissional (25/11/2026).** `lib/services/sessao_service.dart` (interface e `sessaoDePerfil`), `sessao_service_firestore.dart` (app) e `sessao_service_memoria.dart` (testes); o `main.dart` usa a versão Firestore. **Entrar:** o Login e a Abertura com sessão salva chamam `iniciarSessao(usuario)` (`app_state.dart`) **antes** de abrir o Início. ## Como subir sua task (branches)

**Ninguém commita direto na `main` nem na `develop`.** Cada task é feita numa branch própria, criada a partir da `develop`, e só entra na `develop` por Pull Request (PR).

- `main`: versão entregue. Só recebe a `develop` nas entregas.
- `develop`: versão em desenvolvimento, sempre funcionando.
- `tipo/descricao-curta`: uma branch por task. O tipo é o mesmo dos commits (`feat`, `fix`, `test`, `docs`, `refactor`). Exemplos: `fix/barra-inferior-home`, `feat/cadastro-salvar`, `fix/historico-crianca`.

### Passo a passo

```bash
# 1. Atualizar a develop e criar a branch da task
git checkout develop
git pull
git checkout -b fix/barra-inferior-home

# 2. Trabalhar e commitar (mensagens em português)
git add <arquivos>
git commit -m "fix: barra inferior não duplica a Home"

# 3. Antes de subir, conferir se está tudo passando (dentro de appnutrimirim/)
flutter analyze
flutter test

# 4. Subir a branch
git push -u origin fix/barra-inferior-home
```

5. No GitHub, abra um **Pull Request da sua branch para a `develop`**, não para a `main`. No título, use o mesmo padrão dos commits. Na descrição, conte o que mudou e como testar.
6. Peça para **outro integrante revisar**. Depois da aprovação, faça o merge e apague a branch.

### Quando a `develop` mudou enquanto você trabalhava

Se alguém fez merge antes de você (por exemplo, a task de modelos do Davi), traga as mudanças para a sua branch antes de abrir o PR:

```bash
git checkout develop
git pull
git checkout <sua-branch>
git merge develop
# se der conflito: resolva os arquivos, depois "git add" e "git commit"
```

### Cuidados

- Uma branch por task. A task fácil e a difícil ficam em branches separadas.
- Antes de começar, faça commit ou guarde o que estiver pendente. Evite deixar `git stash` esquecido: um stash antigo causou um conflito no `docs/requisitos.md` em 10/11/2026.
- Não suba arquivos gerados (`build/`, `.dart_tool/`), que o `.gitignore` já ignora.
- **Confira o `base` do PR antes de criar.** Ele tem que ser `develop`. Em 11/11/2026 um PR foi mergeado na `main` por engano.
- **Nunca use o botão "Revert" do GitHub num merge.** Em 11/11/2026, reverter um merge na `main` apagou o app inteiro, e isso entrou na `develop`. Se algo entrou errado, peça ajuda antes.
- Se o `flutter pub get` mudar o `pubspec.lock` ou os arquivos `generated_plugin...` sem você ter mexido em dependências, não commite: é diferença de versão do Flutter. Desfaça com `git restore`.
